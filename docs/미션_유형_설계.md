# Travel Bingo 미션 유형 설계

## 1. 기본 원칙

미션은 장소 방문에 종속되지 않는다. 장소는 필요한 미션에만 선택적으로 연결하고, 모든 미션은 공통 진행·인증·보상 흐름을 사용한다.

```text
미션 정의
  → 플레이 시점 정책 스냅샷
  → 사용자 수행
  → 증거 제출
  → 유형별 검증기
  → 승인/반려/검수
  → 빙고 칸·점수·라인 반영
```

## 2. 지원 유형

| 유형            | 예시                    | 주요 증거              | MVP           |
| --------------- | ----------------------- | ---------------------- | ------------- |
| `PLACE_VISIT`   | 공산성 도착하기         | GPS, 정확도, 측정시각  | P0            |
| `WALK_STEPS`    | 제민천 3,000걸음 걷기   | 세션 중 걸음 추정값    | 제한적 P1     |
| `WALK_DISTANCE` | 금강변 2km 걷기         | 위치 표본, 누적 거리   | P0/P1         |
| `QUIZ`          | 백제 역사 문제 맞히기   | 답안, 선택적 위치      | P0            |
| `QR_SCAN`       | 시장 상점 QR 찾기       | 서명 QR                | P0            |
| `PHOTO`         | 지정 구도나 대상 촬영   | 사진, 선택적 GPS       | P0 수동/P1 AI |
| `CHECK_IN`      | 오늘 지역 탐험 시작하기 | 시간, 지역, 선택적 GPS | P0            |
| `COMPOSITE`     | 1km 걷고 사진 찍기      | 둘 이상의 조건         | P1            |

## 3. 데이터 모델

`Mission`은 다음 공통 필드를 가진다.

- `kind`: 미션 유형
- `placeId`: 장소가 필요한 경우에만 설정
- `targetValue`: 3,000걸음, 2km, 5개 장소 등의 목표 수치
- `targetUnit`: `steps`, `meters`, `count` 등
- `verificationPolicy`: 정확도·시간·복합 조건 같은 유형별 정책
- `points`, `difficulty`: 보상과 난이도

`SessionCell.missionSnapshot`에는 위 정책을 플레이 시작 시점 기준으로 복사한다.

`Verification`은 다음 증거를 저장한다.

- 좌표, 정확도, 측정시각, 계산 거리
- 사진 객체 키
- `observedValue`: 실제 걸음 수·거리·개수
- `evidence`: 위치 표본 요약, QR 버전, 답안 결과 등 유형별 구조화 증거
- 판정 상태와 사유

## 4. 검증기 인터페이스

각 유형은 독립 검증기로 구현한다.

```ts
interface MissionVerifier {
  supports(kind: MissionKind): boolean;
  verify(context: VerificationContext): Promise<VerificationDecision>;
}
```

공통 결과:

- `APPROVED`
- `REJECTED`
- `NEEDS_REVIEW`

클라이언트가 제출한 성공 여부나 누적 점수를 신뢰하지 않고 서버가 정책 스냅샷과 증거를 이용해 판정한다.

## 5. 걷기 미션 정책

### PWA 단계

브라우저/PWA만으로 iOS HealthKit이나 Android Health Connect의 시스템 걸음 수를 공통 방식으로 읽을 수 없다. 따라서 MVP에서는 다음 방식을 사용한다.

- 사용자가 미션 화면에서 `걷기 시작`을 누른 뒤 전면 실행 중 측정
- 위치 표본으로 누적 이동거리 계산
- 선택적으로 동작 센서를 보조 신호로 사용
- 비정상 속도, GPS 점프, 지나치게 낮은 정확도 제거
- 화면 종료나 권한 거부 시 측정 한계를 명확히 안내

걸음 수는 센서 기반 추정치이므로 높은 가치의 보상이나 경쟁 이벤트 최종 순위에는 단독 사용하지 않는다. P0에서는 `WALK_DISTANCE`를 우선하고 `WALK_STEPS`는 낮은 보상의 체험 미션으로 제한한다.

### 네이티브 확장

추후 Capacitor 등으로 앱을 패키징하면 사용자 동의를 받아 다음을 연동할 수 있다.

- Android: Health Connect `READ_STEPS`
- iOS: HealthKit step count

건강 데이터 권한은 미션을 시작하는 시점에 필요한 범위만 요청하고, 거부해도 다른 미션을 이용할 수 있어야 한다.

## 6. 퀴즈 미션 정책

- 단일/복수 선택, 숫자, 짧은 문자열 답안을 지원
- 정답 원문 대신 정규화한 답의 hash 저장
- 대소문자·공백·문장부호 허용 규칙을 버전으로 고정
- 현장 퀴즈는 GPS 조건과 결합 가능
- 시도 횟수와 재시도 대기시간 제한
- 문제와 정답이 바뀌어도 진행 중 세션은 snapshot 유지

## 7. 복합 미션 정책

복합 미션은 정책을 조건 트리로 표현한다.

```json
{
  "operator": "ALL",
  "conditions": [
    { "type": "WALK_DISTANCE", "targetValue": 1000, "targetUnit": "meters" },
    { "type": "PHOTO", "requiresLocation": true }
  ]
}
```

- `ALL`: 모든 조건 충족
- `ANY`: 지정 개수 이상의 조건 충족
- 조건별 판정 근거를 별도로 저장
- 전체 승인 전에는 빙고 칸을 완료하지 않음

## 8. 추천 미션 구성 비율

첫 공식 5×5 판은 한 유형에 편중하지 않는다.

| 구성             | 권장 칸 수 |
| ---------------- | ---------: |
| 장소 방문·체크인 |          8 |
| 걷기 거리·산책   |          4 |
| 현장 퀴즈        |          5 |
| QR               |          3 |
| 사진             |          4 |
| 보너스 또는 복합 |          1 |

QR 설치 협조나 사진 검수 인력이 부족하면 해당 칸을 장소 방문·퀴즈로 대체한다.
